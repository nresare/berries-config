# berries-config

This is the config repo for the berries cluster. The top level configuration
lives in [config.toml](./config.toml) and is transformed using
the latest version of [manifest-builder](https://github.com/nresare/manifest-builder) and
committed to [berries-manifests](https://github.com/nresare/berries-manifests).

## Website plugin

The `[[website]]` config block is implemented locally in
[`plugins/website.py`](./plugins/website.py), with its Mustache templates and
tests alongside it. Manifest-builder discovers the block from the top-level
`plugins/` directory when this configuration is loaded.

### Random secrets

Both `[[simple]]` and `[[website]]` support `random-secret = "SESSION_KEY"`
for one key or `random-secrets = ["API_KEY", "SIGNING_KEY"]` for multiple keys.
The two forms cannot be combined. Each generates a `RandomSecret` resource
with the application's Kubernetes name and namespace, and mounts the resulting
Secret at `/random-secrets` in deployment containers. This also works for Hugo
websites and requires the cluster's randomsecret controller.

### Hugo website backend TLS

A `[[website]]` entry that uses `hugo-repo` generates a TLS-only backend. The
generated workload requests an internal certificate from a cert-manager
`ClusterIssuer` named `cluster-local`, serves HTTPS on port 8443, and uses a
Gateway API `BackendTLSPolicy` to validate the service identity
`<service>.<namespace>.svc`.

The target cluster must provide:

- A ready cert-manager `ClusterIssuer` named `cluster-local`.
- A trust-manager `Bundle`, or an equivalent mechanism, that creates a
  `ConfigMap` named `cluster-local-ca` in every namespace containing a generated
  Hugo website.
- A PEM-encoded CA bundle in the `ca.crt` key of each `cluster-local-ca`
  `ConfigMap`.

The issuer, CA lifecycle, and trust-manager installation are cluster-level
concerns and are not generated by individual `[[website]]` entries.
